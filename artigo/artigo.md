# Nove vezes mais requisições com o mesmo limite total de CPU: o gargalo era o trabalho do banco

## 1. Resumo

Ao iniciar o desafio, o sistema proposto apresentava diversos problemas, sendo os principais: API lenta com consultas que realizavam trabalho desnecessário, consumo de CPU desequilibrado: enquanto a CPU do banco sempre estava próxima ao limite, a da API se mantinha praticamente parada. Dado esse cenário, ao longo da atividade, considerei diversas alternativas, testei 13 hipóteses na prática, das quais algumas foram descartadas e outras adotadas. Usei três rodadas para medir cada mudança e conferi separadamente as 42 respostas do contrato. Resultado obtido: a vazão passou de 2,87 para 26,65 req/s (9,29 vezes) e o p95 geral caiu 89,3%, de 21.354,1 para 2.291,5 ms. Além disso, também foi possível remanejar os recursos de CPU disponíveis na API para o banco, no final os recursos ficaram distribuídos como: 1,25 CPU para o banco e 0,25 CPU para a API, utilizando o mesmo limite de 1,5 CPU.

## 2. Contexto e diagnóstico

O sistema é uma API Node com PostgreSQL em Docker, com 7 rotas e estes limites:

| Serviço    | CPU | Memória |
| ---------- | --: | ------: |
| PostgreSQL |   1 | 512 MiB |
| API        | 0,5 | 256 MiB |

Na carga, 20 usuários virtuais usam a API ao mesmo tempo por 60 segundos. Cada um sorteia uma rota, envia a requisição, espera a resposta e envia a próxima, sem pausa. Assim, resposta mais rápida vira mais requisições por segundo.

Na linha de base (mediana de 3 rodadas; [B1](../resultados/20261117-020419-00-linha-de-base/), [B2](../resultados/20261117-020610-00-linha-de-base/), [B3](../resultados/20261117-020801-00-linha-de-base/)):

| Métrica      |       Valor |
| ------------ | ----------: |
| Vazão        |  2,87 req/s |
| p50          |  1.299,9 ms |
| p95          | 21.354,1 ms |
| CPU do banco |       98,5% |
| CPU da API   |        5,9% |

100% = 1 CPU. O banco estava no teto enquanto a API quase não trabalhava. Para descobrir por quê, usei `EXPLAIN (ANALYZE, BUFFERS)` [1] em cada consulta e segui o fluxo de chamadas do código ([leitura inicial](../diagnostico/leitura-inicial.md)).

**Hipótese de causa:** o banco faz trabalho demais a cada requisição. Por rota:

- **Todas as rotas:** cada consulta abria e fechava a própria conexão. (H2)
- **Pedidos do cliente:** a API fazia 17 consultas para os 5 pedidos e 10 itens do cliente 7, e as buscas de pedidos e de itens liam a tabela inteira por falta de índice. (H1, H3, H4)
- **Cliente por e-mail:** sem índice que atenda `lower(email)`, o banco lia 100 mil clientes para devolver um. (H7)
- **Pedidos por status:** a contagem lia todos os pedidos do status, e a página 1000 ordenava em disco antes de pular as anteriores. (H5, H9)
- **Busca de produtos:** buscar um trecho no meio do nome, como "cadeira", impede o índice comum, e o banco percorria todos os produtos.
- **Vendas por dia:** em uma semana, o banco mandava 12.945 linhas para o Node somar por dia. (H8)
- **Top produtos:** o banco juntava o catálogo a todos os itens antes de somar e escolher os primeiros colocados. (H6)

## 3. Estado da arte

### Índices e planos de consulta

Um índice fornece ao banco uma forma de encontrar linhas sem a necessidade de ler a tabela inteira, mas precisa ser mantido nas escritas que alteram os dados indexados [2]. Ele funciona como um índice remissivo de um livro, em vez de folhear todas as páginas, o banco consulta uma lista ordenada e vai direto às linhas que procura. Ele também pode ser criado sobre uma expressão, como `lower(email)`, e servir às buscas que usam a mesma expressão [3]. Selinger e colegas descreveram, no System R, um otimizador que estima o custo de cada caminho de acesso e considera a ordem que ele entrega, comparando com ordenar o resultado depois [4]. Buscas com curinga no início, como `%cadeira%`, pedem outro tipo de índice, por trigramas [5].

### Menos idas ao banco

Em vez de uma consulta por pedido, o PostgreSQL pode comparar um valor com uma lista inteira de IDs (`= ANY(array)`) [6]. Usei isso na H1 para buscar de uma vez os itens de todos os pedidos de um cliente. A Sisense relata o padrão que usei na H6: agregar por ID e buscar os nomes só no fim [7].

### Pool de conexões

Um pool consiste em manter um número de conexões já abertas e realizar as consultas reaproveitando essas conexões a cada requisição, evitando o custo de abrir uma conexão por consulta [8]. O PgBouncer oferece pooling com modos por sessão, por transação ou por instrução [9]. Na minha leitura, ele compensa quando várias instâncias da aplicação precisam compartilhar conexões com o banco.

### Paginação e contagem

O GitLab mantém o `OFFSET`, busca primeiro as colunas de ordenação em um índice compatível e só depois carrega as linhas completas da página [10]. A Shopify propõe outra saída: trocar o número da página por cursores [11]. Não adotei essa troca porque o contrato exige poder pular direto para qualquer página. Uma contagem exata precisa verificar quais linhas são visíveis para cada transação [12].

### Totais pré-calculados

Uma view materializada guarda o resultado de uma consulta e só muda quando é recalculada, ficando defasada entre atualizações [13]. A Crunchy Data compara um ranking de vendas calculado na hora com o mesmo ranking lido de uma view [14].

### Carga, latência e recursos

A Lei de Little relaciona o número médio de requisições em andamento à vazão e ao tempo médio de resposta [15]. Com 20 usuários fixos, resposta mais curta vira mais vazão. Dean e Barroso mostram que a cauda de latência fica mais difícil de controlar quando a utilização sobe [16]. O Docker limita a memória e a CPU de cada contêiner [17].

Em pedidos por status, por exemplo, o cliente precisa poder saltar diretamente para uma página e receber o total exato. A coluna de efeito esperado registra a hipótese antes do teste.

## 5. Solução escolhida e por quê

Escolhi começar pelos pedidos do cliente. A leitura do código mostrava que, à medida que um pedido ganhava itens, a API fazia mais consultas para montar a mesma resposta. Optei por buscar os itens em lote. Uma consulta única com `JOIN` também reduziria as idas ao banco, mas exigiria mais cuidado para reconstruir os pedidos, inclusive os que não tinham itens. Para reaproveitar conexões entre requisições, escolhi o `pg.Pool`, já disponível no driver. Como havia uma única instância da API, preferi o pool do driver ao custo de operar também o PgBouncer.

Para escolher os índices, parti do que cada consulta precisava encontrar. Nos pedidos do cliente, indexei as colunas que ligam o cliente aos pedidos e cada pedido aos seus itens. Na busca por e-mail, indexei `lower(email)`, a expressão usada pela rota. Na paginação, o índice `(status, criado_em DESC, id DESC)` atendia ao filtro e à ordem da resposta, preservando o salto direto por número de página. Tratei a contagem exata separadamente, com um índice menor em `status`.

Nos relatórios, escolhi calcular os totais na hora, a partir dos pedidos não cancelados. Em vendas por dia, retirei `observacoes`, que o Node descartava, e levei a soma para o SQL. Mesmo que um índice de data encontrasse os pedidos mais rápido, a API ainda receberia uma linha por item para fazer a conta. Em top produtos, somei a receita por produto, selecionei os primeiros colocados e só então busquei seus nomes e categorias. Assim, o ranking refletia as vendas sem depender da atualização de uma view materializada.

Por fim, o diagnóstico mostrava o banco próximo do teto de CPU enquanto a API tinha folga. Isso motivou testar a redistribuição da CPU já disponível e, em um experimento separado, a redução do limite de memória da API. Avaliei cada mudança com a mesma carga e com a verificação do contrato.

O [registro de decisões](../docs/decisoes.md) reúne as escolhas, e o [histórico de experimentos](../experimentos.md) contém as hipóteses de cada teste.

## 7. Limites e testes futuros

O banco continua no teto de CPU. Na última coleta por consulta, feita com o `pg_stat_statements` depois da H8, vendas por dia, contagem por status e top produtos somavam 84,5% do tempo de SQL, embora respondam por cerca de um quarto das requisições ([ranking](../diagnostico/pos-h8/ranking.tsv)). A coleta é anterior à H9 e, com o banco saturado, inclui a espera por CPU. Essas consultas precisam ler muitas linhas por natureza, mesmo com os índices atuais. Uma alternativa seria guardar os totais. Uma atualização periódica deixaria o ranking defasado entre atualizações. Manter os totais na mesma transação de cada venda preservaria a exatidão, com custo na escrita.

Os índices ajudaram bastante na busca de pedidos. O que ficou em aberto foi o custo deles na hora de registrar uma venda, porque os 20 usuários do teste só faziam consultas. Eu repetiria a comparação inserindo pedidos e itens para ver quanto tempo leva para salvar uma venda e quanto espaço os índices ocupam. Também rodaria a carga por mais tempo antes de tirar uma conclusão sobre o p95 de top produtos. Na linha de base, foram só três chamadas por rodada. Com tão poucas chamadas, basta uma demorar mais para mudar bastante esse número. [Rodadas da linha de base](../experimentos.md#resultado-da-h1)

Dois resultados me fariam rever o custo-benefício das mudanças. A primeira seria a versão original, só com mais CPU para o banco, chegar a um ganho parecido sem as mudanças nas consultas. A segunda seria uma carga com escritas em que os índices custassem mais do que economizam nas leituras. Não medi nenhum dos dois cenários.

O teste que eu retomaria primeiro é o do pool. Com quatro conexões, o p95 caiu, mas a maioria das rotas ficou mais lenta na mediana. Por isso, mantive dez. Agora eu testaria seis, medindo também quanto tempo cada requisição espera por uma conexão. Para mim, a troca valeria a pena se o p95 voltasse a cair nas três rodadas sem piorar o p50 das rotas mais usadas nem perder vazão. Na busca de produtos, ainda ficou a ideia de testar um índice de trigramas com termos comuns, raros e sem resultados. [Próximos testes](../proximos-testes.md)

## 9. Uso de IA

Empreendi um uso bastante pragmático de IA. Primeiro iniciei solicitando que preparasse um setup adequado para a resolução do desafio, estabelecendo uma skill que orientasse as medições. Depois, defini padrões de versionamento que queria seguir. Pedi uma explicação assistida da API e também de como a carga funcionava objetivando compreender o sistema e os testes. Também me preocupei em manter o sistema e as decisões atualizadas, visando facilitar o trabalho de outros agentes no projeto. Após isso meu uso se concentrou principalmente em 2 frentes:

1°: Identificação de gargalos de performance e de consultas pouco eficientes, levantamento de alternativas de solução e pesquisa de fontes variadas para estudo. Sempre verifiquei as informações trazidas pela IA por meio da leitura das fontes e dos conteúdos recomendados, buscava entender a aplicação deles no contexto do código, solicitava comparações entre alternativas e descartava fontes quando as achava improdutivas, sempre tentando obter conhecimento acerca das propostas antes de tomar uma decisão definitiva. Resumindo meu objetivo em poucas palavras: minha preocupação era em não apenas carimbar as alternativas sugeridas pela IA, mas entender a solução por completo.

2°: Medições e análise dos números, deixei a IA responsável pela parte exaustiva e repetitiva, rodar as três medições, conferir o contrato, depois diagnosticar o impacto das mudanças na performance em comparação com a linha de base e fazer o trabalho de contas. Com o resultado, eu analisava o custo-benefício de cada alternativa.

Além disso, fiz um uso minoritário na manutenção do md de experimentos, onde utilizei a IA para redigir as nossas hipóteses, as decisões tomadas e as previsões discutidas em diversos prompts em um texto consolidado. Na redação do artigo, usei a IA para organizar as alternativas, calcular os percentuais, redigir e revisar trechos das seções e conferir as referências com o registro de fontes. As duas principais LLMs que empreguei foram os modelos da OpenAI e Anthropic, o ChatGPT foi o principal executor e pesquisador, enquanto utilizei o Claude como orquestrador e revisor de que estávamos no caminho certo proposto no desafio.
